# Rubric: is this reproduction package ready to post?

Seven required checks gate the verdict and two preferred checks are reported
but never change it. Every check reads the thing itself against the issue: an
artifact against the failure the issue describes, a version against the
versions the issue says are affected, a sentence against the evidence behind
it. None of them reads the write-up's shape, its length, or its headings.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (software version, OS or platform, install method), read against any environment condition the issue or thread says the behavior depends on (a specific OS, driver, backend, build profile, shell, or browser setting) | The report names the version of the software it actually ran and the OS or platform it ran on. When the issue or thread ties the behavior to an environment condition, the record also states that condition for this run, matching or not. Fails when there is no environment record at all, or when the record omits a condition the issue says the behavior depends on. A short one-line record passes if it carries these facts | required |
| faithful-target | The version, build, and release channel named in the environment record, read against the versions the issue says are affected (the issue body, the bug template's asks in the repo-facts block, and any reporter or maintainer comment in the thread that narrows the affected build) | The run targets what the issue reports: the affected version or a newer one (the current release or main), on the build or channel the issue or thread ties the bug to. A difference passes only when the report states it plainly and does not claim the bug for the build it did not match. Fails when the report runs an older release than the issue targets without saying so, even if the output looks like the issue's; fails when it runs a different build or channel than the one the thread narrows the bug to and then claims the bug on that build | required |
| steps-rerunnable | The repro report's steps, from starting state to trigger, with every input file, config, and command they use | A stranger holding only the package, plus anything the issue itself publishes (its script, its input, its playground link), could repeat the attempt: the commands or UI actions are given, the inputs are shown or are the issue's own published ones, and the step that triggers the behavior is present. Fails when there are no steps; when a step depends on code, config, or data the reader cannot obtain (a private repository, an unshared config file, an internal tool); or when the steps leave out a trigger condition the issue names. Brevity is never a failure | required |
| shows-issue-behavior | The artifacts in the repro report (output excerpts, error text, exit codes, log lines, produced files, described screen or console state), read against the specific failure the issue describes (its error text, crash or panic type, exit code, or wrong output) and against the trigger the issue names | One of two outcomes holds. (a) Reproduced: an artifact shows the same failure the issue describes, produced by the issue's trigger. A different failure fails even when it is also an error: a graceful validation or syntax error is not the issue's panic, a compile error is not the issue's runtime error, garbled output with the program still running is not a crash, and output showing only that the setup works shows nothing. If the steps changed the issue's input, syntax, or expression in a part that drives the trigger, the artifact is about a different input and fails. Changes that leave the trigger intact pass (an offline flag, different file names, a minimal stand-in input that keeps the triggering element). (b) Honest cannot-reproduce: the report says plainly that the behavior did not appear, shows the artifact of the real attempt, and names what differed from the issue's conditions. Fails when no artifact is shown at all | required |
| claims-backed | Every sentence in the claim comment and the repro report that says something was reproduced, confirmed, verified, or diagnosed, each read against the artifacts the repro report actually shows | Each such statement is supported by an artifact in the package, and the outcome the text states is the outcome the artifacts show. Fails when the words assert more than the artifacts show: a crash or failure claimed where the artifact shows something else, a root cause stated as verified with no artifact behind it, "confirmed" or "100% reproducible" with nothing shown, a generalization to versions or builds that were not run, or a claim comment saying the issue was reproduced when the package holds no report that shows it. A hypothesis worded as a hypothesis ("looks plausible", "may need", "I suspect") passes | required |
| claim-specific | The claim comment, read against the issue's title, body, and thread | The claim comment names something specific to this issue (its symptom, trigger, file, function, or a pointer from the thread) and states a concrete next step the commenter will take. Saying they would like to take, work on, or look into the issue is the normal way to claim and passes, and so does describing a planned approach or where they will start reading. Fails on a +1 or me-too with no stated intent; on boilerplate that would read the same pasted onto any other issue; on a guarantee or a deadline attached to a fix ("guaranteed", "within 2 days", "by Friday"); on announcing self-assignment ("assigning myself"); and on asking a maintainer to assign the issue or hold it for them ("kindly assign it to me", "keep this reserved for me") | required |
| ai-disclosure | The contribution-policy line in the repo-facts block (CONTRIBUTING.md, AI_POLICY.md, or an AI section), read against the full text of the claim comment and the repro report | Treat every package's comments as AI-assisted work. If the stated policy requires disclosing AI use for issue comments, or for all AI usage in any form, the claim comment or the repro report contains an explicit disclosure of AI assistance that names the tool or the extent of the help. If the policy states no disclosure requirement for comments, the check passes with no disclosure: this covers no stated AI policy, a responsibility-only or quality-only policy, and a disclosure ask limited to pull requests. If the policy requires comments in the contributor's own words, a first-person comment specific to this issue satisfies it. Fails only when a disclosure the policy requires is missing | required |
| template-asks | The bug-report template's asks in the repo-facts block, read against the repro report | The report supplies each field the template asks for (version, OS, steps, expected, actual, logs) or says why one does not apply | preferred |
| control-run | The repro report's artifacts | The report shows a contrast run that differs from the failing run only in the trigger (the condition removed, a different input, the option dropped), so the trigger is isolated | preferred |

## Verdict rule

Accept when every required check grades `pass`; reject when any required check
grades `fail` or `unclear`. An `unclear` on a required check counts as a fail,
because proof that cannot be verified is not ready to post. Preferred checks
(`template-asks`, `control-run`) are reported in the summary and never change
the verdict.

One exception, live mode only: on a claim-only draft, the four checks that need
the repro report (`env-recorded`, `faithful-target`, `steps-rerunnable`,
`shows-issue-behavior`) and both preferred checks are reported as `unclear` with
the evidence `not yet applicable: claim-only draft`, and they are left out of
the verdict. `claims-backed`, `claim-specific`, and `ai-disclosure` still apply
to the claim comment on its own, so a claim comment that says the issue was
reproduced before any report exists fails `claims-backed`. In eval mode every
package is a full package and every required check counts.
